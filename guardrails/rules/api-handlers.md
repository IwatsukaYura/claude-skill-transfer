`src/handlers/` 配下のファイルを読み書きするときだけロードされる。
`src/lib/db.ts` を触っただけではロードされない。`/context` で確認できる。

## A. コードから読み取れること

- 引数は `RequestContext` を受ける
- パスパラメータは存在チェックしてから使う
- エラーは `ApiError` のファクトリで投げる
- 単一リソースを返す前に `ctx.userId` と `user_id` を照合する。一覧は `filter` で絞る
- DBを変更する操作は必ず `await` する

## B. リポジトリのどこかには書いてあること

- **B-1.** 金額を含むレスポンスを返すハンドラは `audit.recordAccess()` を呼ぶ
  （`src/lib/audit.ts`。既存ハンドラは未バックフィル）
- **B-2.** ハンドラを追加したら `docs/api.md` の表に行を足す
  （ソースからは参照されていないが、公開APIドキュメントの生成元）

## C. リポジトリのどこにも書いていないこと ★rules の存在理由

**C-1. レスポンスの日時は必ず JST（`+09:00`）。UTC で返してはいけない。**

初期のクライアント実装がタイムゾーンを解釈せず表示しているため、
UTC を返すと画面に9時間ずれた時刻が出る。**`toISOString()` をそのまま使わない。**

```ts
// "2026-08-03T22:15:00+09:00" の形にする
const jst = new Date(Date.now() + 9 * 60 * 60 * 1000)
  .toISOString()
  .replace(/\.\d{3}Z$/, "+09:00");
```

この事実はリポジトリのどこにも書かれていない。過去の障害の記憶としてしか存在しない。
**だからこのファイルに書く価値がある。**

**C-2. 金額フィールドは税抜。税込みを返す場合はフィールド名を `_incl_tax` で終わらせる。**

会計システム側が税抜前提で取り込んでいる。`total_jpy` は税抜。
税込みが必要なら `total_incl_tax_jpy` を別に足す。既存フィールドの意味は変えない。

**C-3. 新しいハンドラのテストは3本。** 正常系 / 存在しないIDで404 / 他人のリソースで403。
