# TDDで実装する

対象: $ARGUMENTS

**このスキルの目的は「速く正確に」ではなく「サイクルを飛ばさないこと」。**
1サイクルずつ、順番を守って進める。

## フェーズ0: テストケースを列挙する

`test-designer` サブエージェントに委譲する。

```
test-designer サブエージェントで SPEC.md のテストケースを列挙して。
```

隔離された文脈で仕様書だけを読ませる。実装の都合を知らない状態でケースを出させるため。

返ってきたリストを**そのまま表で人間に見せて、着手前に確認を取る。**

```
| # | ケース | 入力 | 期待値 | 根拠(ルール) |
|---|---|---|---|---|
```

**ここで人間が「これが抜けている」と言えることが、この工程の価値。**
実装が始まってからでは指摘のコストが上がる。

## フェーズ1〜N: 1ケースずつ Red → Green

**リストの上から1件ずつ。まとめて進めない。**

### Red

1. `tests/` にそのケースのテストを**1本だけ**足す
2. 保存すると PostToolUse フックが自動でテストを走らせ、結果が返る
3. **RED になったことを確認する。** 想定と違う理由で落ちていないかを見る
   （型エラーで落ちているのか、アサーションで落ちているのか）

### Green

4. **そのテストを通す最小の実装だけ**を書く
5. フックが返した結果で GREEN を確認する
6. **先回りしない。** リストの次のケースに必要な分岐を、まだ書かない

> `src/` を編集しようとして `require-red` フックが `ask` を出したら、
> それは**まだ Red が無い**という意味。テストを書く工程を飛ばしている。
> 承認を求めるのではなく、テストを書きに戻る。

### 記録

各サイクルの終わりに1行だけ報告する。

```
[3/9] 複数税率のとき税率ごとに税額を計算する → RED → GREEN (pass 6/6)
```

## 最終フェーズ: リファクタ

全ケースが緑になってから。

1. 重複を消す。端数処理が散っていたら `src/money.ts` に寄せる
2. `npm run lint` で型を確認
3. **リファクタ中にテストは1本も変えない。** 変えたくなったら、それは
   リファクタではなく振る舞いの変更

この段階では全部緑なので `require-red` フックが `ask` を出す。
**リファクタなので承認して進む**——これが `ask` の正しい使い方。

## 完了報告

```
| # | ケース | 結果 |
|---|---|---|
（全ケース）

テスト: pass N / fail 0
型チェック: OK
サイクル数: N
先回りして書いた実装: なし
```

`tdd-gate` フック（Stop）が実際に `npm test` を走らせて確認するので、
**通っていない状態では終了できない。** 自己申告は要らない。
